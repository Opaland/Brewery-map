# S283 — `npm audit` dans la CI *(epic E27, persona : Léa)*

## Objectif

Léa n'ouvre jamais une page qui embarque une bibliothèque à faille connue
de gravité haute ou critique : la porte refuse de la publier, et une alerte
nouvelle sur les outils se voit le lendemain matin.

## Pourquoi maintenant

- Repris d'ÉtapeForge (`.github/workflows/ci.yml`), inventaire du 18/10
  (`docs/DEPOTS-FRERES.md`).
- `npm audit` ne tourne nulle part : la revue globale (`/revue-globale`) le
  lance à la main, une fois.
- Mesuré le 18/10 : `npm audit --omit=dev` → 0 vulnérabilité ; l'arbre
  entier → 2 « modérées », `esbuild` ≤ 0.24.2 sous `tsx` (outil de
  développement ; l'avis vise le serveur de développement d'esbuild, que
  `tsx` ne lance pas).

## Critères d'acceptation

| # | Étant donné… quand… alors… | Prouvé par |
|---|---|---|
| CA1 | La porte refuse une faille **haute ou critique** dans ce que la page embarque (`npm audit --omit=dev --audit-level=high`), avant le build | `.github/workflows/ci.yml` ; `tests/unit/ci.test.ts` (vu rouge : l'étape retirée, ou rendue non bloquante) |
| CA2 | L'arbre entier (outils compris) est audité dans la porte sans la bloquer, et chaque nuit dans `sonde-nuit.yml`, où un échec rougit le run du matin | idem |
| CA3 | La commande échoue bien quand l'arbre a une faille au niveau demandé | `npm audit --audit-level=moderate` sur l'arbre du 18/10 : code 1 (les deux « modérées ») ; `npm audit --omit=dev --audit-level=high` : code 0 |

## Choix, dit (§2)

Bloquant pour ce que la page embarque, au niveau « haute » : une faille
« modérée » d'une dépendance de développement rougirait toutes les PR pour
un avis qui ne touche pas la page publiée. Écartés : tout bloquer (une PR
sans rapport deviendrait rouge du jour au lendemain), rien bloquer (une
bibliothèque livrée vulnérable partirait en ligne).

## Hors périmètre

- Mettre `tsx` à jour pour les deux « modérées » : un changement de
  dépendance, à faire dans sa propre story (BACKLOG).
