# S296 — Les bases d'étape de la garde de `data/` *(revue d'architecture S295, AR1 ; persona : Cédric)*

## Objectif

Cédric peut faire évoluer le schéma des fiches (un identifiant stable,
S231 ; un champ retiré) sans que la garde de `data/` refuse l'histoire
déjà acceptée.

## Pourquoi maintenant

- La garde rejoue chaque accord depuis le fichier du 15/10, avec le schéma
  et le code d'aujourd'hui (`src/core/garde-donnees.ts`). Un champ
  obligatoire ajouté, un arrondi de `distanceKm` changé, une règle de
  `ajoutSchema` resserrée la rendent rouge sans qu'aucune donnée ait bougé.
- S231 (l'identifiant stable) en a besoin ; S294 aussi, s'il touche au
  schéma.

## Critères d'acceptation

| # | Étant donné… quand… alors… | Prouvé par |
|---|---|---|
| CA1 | Un accord de type « base », signé par Cédric, cite un commit de `main` où la garde est verte, et le SHA-256 de `data/breweries.json` à ce commit ; la garde part de cette base et ne rejoue que les accords postérieurs | `tests/unit/garde-donnees.test.ts`, vu rouge sans la base |
| CA2 | Une base dont le SHA-256 ne correspond pas au fichier relu dans git est refusée | idem |
| CA3 | Deux bases : la plus récente gagne ; un accord antérieur à elle n'est plus rejoué | idem |
| CA4 | `docs/ARCHITECTURE.md` (§ la garde) et `docs/DECISIONS.md` disent ce qu'est une base, et qui la signe | relecture |

- Écrire la première base : c'est un accord de Cédric.
