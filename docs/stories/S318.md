# S318 — Ce qu'un agent écrit est lu par un schéma *(epic : les outils de curation ; persona : Cédric)*

## Objectif

Une lecture d'agent mal formée, ou dont la clé ferait écrire hors de son
dossier, est refusée avec sa raison au lieu d'être utilisée telle quelle.

## Pourquoi maintenant

BACKLOG, « Relecture d'ensemble S295 — restes », LD9 : des entrées
écrites par des agents lues sans schéma (`JSON.parse(...) as T`), par
exemple `outils/departement.ts` (`lectures`, `assembler`).

Lu le 20/10 dans `outils/departement.ts`, fonction `lectures` : chaque
`LectureAgent` sert à géocoder (`l.adresse`, `l.c`) et à nommer le
fichier écrit, `${dossier}/${l.cle.replace(/[:/]/g, '-')}.json`. Seuls
`:` et `/` sont remplacés : sous Windows, une clé contenant `..\` écrirait
hors de `curation/dep-XX-lectures/`. Une clé vient d'un agent, donc d'une
page lue sur le web : c'est une entrée non sûre (CLAUDE.md §0, sécurité
d'abord).

## Le choix

1. `lectureAgentSchema` (Zod, `src/core/candidats.ts`) : la forme de
   `LectureAgent`, et `lireLecturesAgent(brut)` qui rend les lectures ou
   les erreurs (chemin et message), comme `lireLot`.
2. `nomDeFichierDeLecture(cle)` : seuls lettres, chiffres, `.`, `_` et `-`
   restent ; pas de point en tête ; jamais vide.
3. `outils/departement.ts` s'en sert : un fichier invalide est refusé en
   entier, avec ses erreurs.

Hors périmètre : les autres `JSON.parse … as` des outils, qui lisent des
fichiers produits par le dépôt lui-même ou des API publiques dont la
réponse est relue ensuite (géocodeur, SIRENE).

## Critères d'acceptation

| # | Étant donné… quand… alors… | Prouvé par |
|---|---|---|
| CA1 | Une lecture valide passe ; un champ manquant ou d'un mauvais type est refusé avec son chemin. | `tests/unit/candidats.test.ts` (rouge avant). |
| CA2 | `..\\..\\src\\x`, `../x`, `a/b:c`, `..` : le nom produit ne contient ni séparateur ni `..` en tête, et n'est jamais vide. | `tests/unit/candidats.test.ts`, et le fuzz de S282 si la fonction y entre. |
| CA3 | `outils/departement.ts lectures` lit par le schéma et nomme par la fonction. | lecture du code ; `tsc -b`. |

## Décisions de Cédric requises

Aucune.

## Porte qualité

Verdict : **PASSE.** Revue adverse : deux failles de nommage et deux
points, traités :
- deux clés vers le même fichier (`osm:node/1` et `osm-node-1`, ou deux
  clés qui ne diffèrent que par la casse sous Windows) : la seconde
  écrasait la première sans bruit. `lireLecturesAgent` les refuse ; test ;
- une clé de 300 caractères faisait planter l'écriture sous Windows au
  milieu de la boucle : `cle` bornée à 120 caractères ; test ;
- ce que ce schéma laisse passer (source `javascript:`, catégorie 99) est
  bien refusé ensuite au schéma d'un ajout (`assemblerLot`) : test ;
- `assembler` relit toujours les fichiers déjà écrits sans schéma, avec
  `typeof candidat` seul : ces fichiers sont écrits par `lectures`
  elle-même, et chaque `ajout` passe au schéma dans `assemblerLot`. Laissé
  ainsi, et dit ici.

Les 15 fichiers réels `curation/dep-*-lus.json` (192 lectures) passent
le schéma. CA2 rougit avec l'ancien nettoyage (mutation à la main).
